# EduEdge AI — Backend API Guide (for the frontend/Flutter side)

This explains exactly what the backend gives you, how to call it, and
how to wire it into the app instead of `MockService`. Everything below
has been tested against a running server, not just written on paper.

---

## 1. Where the backend lives

Once it's running on the backend teammate's machine:

- **Android emulator**: use `http://10.0.2.2:8000` — this is already
  what's in `lib/core/constants/api_constants.dart`, so no change
  needed there. `10.0.2.2` is the emulator's special alias for the
  host machine's `localhost`.
- **Real physical phone**: `10.0.2.2` will NOT work. You'll need the
  backend machine's LAN IP instead (e.g. `http://192.168.1.5:8000`),
  and both the phone and that machine must be on the same Wi-Fi.
  Ask the backend teammate for the current IP when you're testing this
  way — it can change between networks.
- **Interactive API docs**: `http://<baseUrl>/docs` — this is
  auto-generated by FastAPI. You can try every endpoint by hand in the
  browser before writing any Dart code, which is the fastest way to
  see the exact JSON shape without guessing.

## 2. The 5 endpoints you asked for

All 5 are live and tested. Base path for all of these is just the
`baseUrl` above — no `/api/v1` prefix, matching what's already in your
`api_constants.dart`.

### `GET /health`

Sanity check — confirms the server is up before you debug anything
else.

**Response 200:**
```json
{ "status": "ok" }
```

### `POST /auth/login`

**Request body:**
```json
{ "email": "student@eduedge.com", "password": "test1234" }
```

**Response 200 (success):**
```json
{
  "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "user": { "name": "Student" }
}
```

**Response 401 (wrong email/password):**
```json
{ "detail": "Invalid email or password" }
```

A test account already exists for you to log in with right away:
```
email: student@eduedge.com
password: test1234
```
If you need more test accounts, ask the backend teammate to add them
via the seed script, or use the real registration endpoint at
`POST /api/v1/auth/register` (note: that one's under `/api/v1`, needs
`full_name` + `email` + `password` ≥ 8 characters).

**Note on the token:** it's a real signed JWT, not a fake string. You
don't need to do anything with it yet for these 5 endpoints — none of
them require it. Just store it (e.g. in memory or `shared_preferences`)
for when protected endpoints get added later (progress tracking, etc.).

### `GET /lessons`

**Response 200:**
```json
[
  {
    "id": "1",
    "title": "Introduction to Photosynthesis",
    "subject": "Biology",
    "icon": "🌿",
    "content": "Photosynthesis is the process by which..."
  },
  {
    "id": "2",
    "title": "Newton's Laws of Motion",
    "subject": "Physics",
    "icon": "⚡",
    "content": "Newton's three laws of motion form..."
  },
  {
    "id": "3",
    "title": "World War II Overview",
    "subject": "History",
    "icon": "📖",
    "content": "World War II was a global conflict..."
  }
]
```

This is intentionally the exact same 3 lessons your `MockService`
already has — same ids, same fields — so your existing UI code that
reads `lesson['title']`, `lesson['icon']`, etc. doesn't need to change
shape at all when you switch from mock data to this real endpoint.

### `GET /lessons/{id}`

e.g. `GET /lessons/2`

**Response 200:** single lesson object, same shape as one item above.

**Response 404 (bad id):**
```json
{ "detail": "Lesson not found" }
```

### `POST /ai/summarize`

**Request body (either field works, both optional):**
```json
{ "lessonId": "1" }
```
or
```json
{ "text": "some lesson content..." }
```

**Response 200:**
```json
{
  "summary": "This is a placeholder AI-generated summary. Once the AI engine is connected, this will be a real summary of the lesson content."
}
```

This one is **hardcoded on purpose** — always returns the same
placeholder string no matter what you send it. The real AI engine
(built by the third teammate) isn't wired in yet. When it is, this
same endpoint URL and response shape will start returning a real
summary — you won't need to change anything on your end.

## 3. What's temporary vs. permanent (so you know what might shift)

| Endpoint | Status |
|---|---|
| `GET /health` | Permanent, part of the real API |
| `GET /lessons`, `GET /lessons/{id}` | **Temporary bridge.** Backed by a small demo table with just these 3 lessons. Once the real content system (subjects/grades/chapters, synced from the AI engine's content pipeline) is ready, these will likely be replaced by richer endpoints — the backend teammate will tell you if/when the shape changes. |
| `POST /auth/login` | Permanent endpoint, but this specific response shape (`{token, user:{name}}`) is a simplified version of the real one at `/api/v1/auth/login`, which returns more user fields (`id`, `email`, `role`, `is_active`) and `access_token`/`token_type` instead of `token`. If you ever need those extra fields, ask about switching to the `/api/v1` version. |
| `POST /ai/summarize` | Permanent URL, but hardcoded response until the AI engine integration lands. |

## 4. How to actually wire this into your Flutter code

Right now, based on the code you shared, nothing in the app is making
real network calls yet:

- `auth_provider.dart`'s `login()` just does a fake `Future.delayed`
  and checks `password.length >= 4` locally — it never touches the
  network.
- `lesson_screen.dart` reads straight from `MockService.lessons`.
- The AI screen presumably does something similar for summarize.

To connect for real:

1. **Add an HTTP client package** to `pubspec.yaml` if you don't have
   one already — `http` is the simplest, `dio` if you want
   interceptors/logging later.

2. **Replace `AuthProvider.login()`** to POST to
   `ApiConstants.baseUrl + ApiConstants.login`, parse the JSON response
   into `token` and `user.name`, and store both in the provider instead
   of the fake locally-computed name.

3. **Replace `MockService.lessons`** usage in `lesson_screen.dart` (and
   wherever else it's used) with a real GET call to
   `ApiConstants.baseUrl + ApiConstants.lessons`, decode the JSON array
   into your lesson objects. Same for the single-lesson fetch if you
   have one, using `ApiConstants.lessons + '/$lessonId'`.

4. **Wire the "Summarize with AI" button** to POST to
   `ApiConstants.baseUrl + ApiConstants.summarize` with `{"lessonId":
   lesson['id']}`, and display the returned `summary` string. Since
   it's hardcoded server-side right now, you'll see the same placeholder
   text every time — that's expected, not a bug on your end.

5. **Handle errors.** At minimum:
   - Network/connection failures (backend not running, wrong IP,
     emulator vs. real device confusion) — show a retry state.
   - `401` on login — show "invalid email or password", don't crash.
   - `404` on a lesson fetch — show a "lesson not found" state rather
     than assuming the list result.

## 5. Quick way to sanity-check the backend yourself

Before touching any Dart code, you can hit these directly from a
terminal or browser to confirm what's really coming back:

```bash
curl http://<baseUrl>/health

curl -X POST http://<baseUrl>/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"student@eduedge.com","password":"test1234"}'

curl http://<baseUrl>/lessons

curl http://<baseUrl>/lessons/2

curl -X POST http://<baseUrl>/ai/summarize \
  -H "Content-Type: application/json" \
  -d '{"lessonId":"1"}'
```

Or just open `http://<baseUrl>/docs` in a browser and click "Try it
out" on each endpoint — no curl needed.
